# Setup and model configuration

## Sub-features

Installed setup invocation, harness-to-provider mapping, generated routing/model preferences, unavailable-provider handling, and changed configuration references.

## How to get to it (user POV)

Invoke `/pstack:setup-pstack` in Claude or `$setup-pstack` in Codex. The installed instructions are the authority for setup inputs.

## Driving it with verify-open-pstack

For setup only, snapshot the operator's real `${CLAUDE_CONFIG_DIR:-$HOME/.claude}/pstack-models.md` and `CLAUDE.md` before invocation, preserving exact bytes and whether each file existed. Exercise every changed setup branch with explicit model/provider inputs. Retain the native transcript and generated configuration privately, then invoke a consuming installed skill to observe the configured route.

Restore both files byte for byte afterwards, including restoring original absence, on success or failure. Verify restoration before any evidence comment or status publication. Restoration failure stops the run and publishes nothing. Retain snapshot and restoration results in the private mode-0700 evidence root through merge.

## Gotchas

Claude uses the operator's normal config/login; Codex uses a run-owned home with auth symlinked to the daily login. Do not redirect `HOME`, copy credentials, start login, or use a mock as setup proof. Generated configuration alone does not prove the consuming surface. Setup restoration is the only permitted temporary change to these daily Claude files.

## Headless

The setup recipe in `recipes.ts` serves `setup` and `skill-invocation:setup-pstack`. One session, `configure`, runs setup with explicit answers that move every model-family role to `claude:opus@high` and answer yes when setup asks whether Codex writer lanes should run with full access. Setup keeps an existing setting line without asking, so before the session the case removes any `codex writer sandbox:` line from the operator's sheet and keeps every other byte. It asserts that the written sheet holds only that descriptor and exactly one setting line, `codex writer sandbox: full-access`. A second session has `poteto-mode` report the configured route for one role. A third, `keep-predecessor`, writes a sheet whose every family lane is `grok:grok-4.6@high`, a kept predecessor, with one alias role left out, and asks setup to decline the replacement. It asserts the rewritten sheet keeps `grok:grok-4.6@high`, restores the missing role, and that the reported proposal is the family's current model from the installed catalog at the same effort. A fourth, `new-families`, writes the installed catalog's role defaults with `swarm workers` on `codex:gpt-6-luna@max`, `hardest tasks` on the registered pin `claude:claude-opus-5-5@max`, `how explainer` on the versioned `claude:claude-sonnet-5-5@max`, and `judgment and prose` on the older revision `claude:claude-opus-5@max`, and asks setup to keep every assignment and effort. On Codex it removes the run-owned `AGENTS.md` mirror first. It asserts that every role line of the rewritten sheet equals the prepared line, except that the versioned revisions are written as `claude:sonnet@max` and `claude:opus@max`. A fifth, `read-only-provider`, writes the installed catalog's role defaults with the read-only role `how explorer` on `opencode:opencode/deepseek-v4.1-flash-free@max`, a provider whose route table lists no bounded `isolated-write`, and asks setup to keep every assignment and effort. On Codex it removes the run-owned `AGENTS.md` mirror first. It asserts that every role line of the rewritten sheet equals the prepared line. A sixth, `writer-refusal`, assigns the writer role `bug-fix` to `opencode:opencode/deepseek-v4.1-flash-free@max`, whose writer needs an `opencode writer sandbox: full-access` line, and asks setup to keep every assignment and decline every writer sandbox opt-in. It asserts that the sheet keeps its exact bytes, that Codex's removed mirror is not written back, and that setup's refusal names the role and the provider. A seventh, `keep-setting`, writes the installed catalog's role defaults with one alias role left out and the line `codex writer sandbox: full-access`, and asks setup to keep every assignment and effort. On Codex it removes the run-owned `AGENTS.md` mirror first. It asserts that the rewritten sheet holds that setting line exactly once and that its role lines equal the role defaults. An eighth, `first-run`, removes the sheet (and, on Codex, the run-owned `AGENTS.md` mirror) and asserts that setup writes a sheet whose role lines equal the installed catalog's role defaults. Every role-line comparison leaves out the setting line. Setup asks about full access when the sheet has no setting line, and declining is the default. So `keep-predecessor`, `new-families`, `read-only-provider` and `first-run`, which start without a setting line and take the default answers, each assert that the written sheet holds exactly one setting line, `codex writer sandbox: bounded`. A missing setting line or an unrequested `full-access` fails them. `writer-refusal` keeps its exact-bytes check: its prepared sheet has no setting line, and setup writes nothing. Every case that removes the Codex `AGENTS.md` mirror also asserts that setup wrote it back: exactly one begin marker and a newline, the rewritten sheet's exact bytes, and one end marker. The parent snapshots the daily files before the first session and restores and verifies them after the last, on success or failure.
